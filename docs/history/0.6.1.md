# 0.6.1: failure-aware review and a build check before review

Spec: [SPEC](../0.6.1/SPEC.md). Build log: [PROGRESS](../0.6.1/PROGRESS.md). A patch release on 0.6.0, released on 15 November 2026.

0.6.1 shipped in three PRs: part 1 (#38), part 2 (#47) and a build check fix found in preview testing (#48). Part 2 adds two additive migrations, one read endpoint and additive API fields. There is no breaking API change and no new error code.

## What changed

- **Branch names.** New project branches are `tevrin/<slug>-<id>` and new release-version branches are `tevrin/<slug>/v<version>`. Projects that already have an `aide/` branch keep it. Branch control now blocks every prefix the project uses.
- **Scrollbars.** A thin, themed scrollbar replaces the browser default in the app and on the marketing site. It follows light and dark, and is CSS only.
- **Failure-aware review.** When a build, deploy or CI check fails, review gets the redacted log excerpt and writes a specific fix step from it. Tevrin attaches a Failure evidence block to that step. A failure that repeats across cycles is marked, and the agent must try a different fix.
- **Deployment files in plans.** Each deploy pack declares the config files it needs. The plan prompt names them. When a plan leaves one out, Tevrin adds a step to create it, marked **Added by Tevrin**.
- **Every deterministic finding is acted on.** Dependency, endpoint, secret, stack and Vercel config findings get a stable id. The optimisation plan must fix each one in a step that names the id, or waive it with a reason. Tevrin adds a step for any finding that has neither. A valid waiver removes the finding's penalty, and the report shows how each finding was handled.
- **More accurate checks.** Catch-all spec paths are read whole, file-based routes and files in `public/` count as endpoints, and only runtime dependencies are checked against the allowlist.
- **A build check before review.** After execution, Tevrin waits for the preview build and the required CI checks on the pushed commit. When one fails, a build-fix agent plans fix steps from the logs, the coding agents run them, and Tevrin checks again. This repeats up to the project's **Build fix attempts** setting (0–10, default 5) before review starts. The execution page shows each attempt as a build card and a fix card.

New requirements are FR-232 to FR-259. Prompts `code_review` and `plan_generator` move to v10 and v7, and `build_fix` v1 is new. The stack catalog moves to 1.2.2.

## Data and API

- New table `build_checks`, with an `end_reason` column added by a second migration. `execution_steps` gains `origin` and `build_check_id`, and `projects` gains `max_build_fix_attempts`.
- New endpoint `GET /api/projects/{projectId}/versions/{versionId}/build-checks`, and a `buildCheckUpdated` event on the execution stream.
- Build check items carry `endReason` and `fixPlanning`, and each source its `status` and `message`. Project DTOs gain `maxBuildFixAttempts`. Execution steps gain `origin`, `buildCheckAttempt` and `buildCheckId`. Review findings gain `findingId`, `handling`, `stepNumber` and `waivedReason`.
